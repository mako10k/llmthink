# SQLite lifecycle control-plane schema

## 1. Status

Status: implementation-ready schema design under accepted ADR-0012. This document does
not authorize code changes, data migration, Stage deployment, or Production activation.

The schema keeps registry, agreement, account lifecycle, tenant/workspace catalog, scope,
recovery, and realization responsibilities logically separate while using one SQLite write
transaction for invariants that cannot safely be split.

Thought bodies, thought revisions, audit bodies, OAuth tokens, email addresses, display
names, and filesystem paths are deliberately absent.

## 2. Database profile

On every connection, before serving requests:

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA busy_timeout = 5000;
PRAGMA trusted_schema = OFF;
PRAGMA recursive_triggers = OFF;
```

Requirements:

- SQLite 3.37 or later is required for `STRICT` tables.
- The process opens an explicit absolute path with no symlink traversal at the final path.
- Database, `-wal`, `-shm`, backup, and restore-candidate files use the same protected
  owner/group boundary. They are never served by HTTP or included in package artifacts.
- `foreign_keys`, `journal_mode`, `synchronous`, and `trusted_schema` are read back and
  checked. An unsupported or weakened effective value fails startup.
- Normal request handlers do not run DDL, `ATTACH`, extension loading, arbitrary PRAGMA,
  `VACUUM INTO` to client-selected paths, or user-supplied SQL.
- One bounded connection owner serializes schema migration. Request transactions use a
  bounded retry policy for `SQLITE_BUSY`; exhaustion returns a privacy-safe unavailable
  state and does not retry an agreement action blindly at the HTTP layer.

WAL permits concurrent readers but still has one writer. Initial provisioning therefore
uses a short `BEGIN IMMEDIATE` transaction and performs no network, filesystem, hashing-KDF,
or terms rendering work while holding the writer lock.

## 3. Identifier and encoding rules

- Internal IDs are server-generated hosted IDs with type prefixes, for example `acct-`,
  `subj-`, `tenant-`, `ws-`, `terms-`, `receipt-`, `prov-`, and `outbox-`.
- External issuer and subject validation happens before persistence and remains exact.
- Optional WorkOS `org_id` is encoded internally as `organization_key = ''` when absent.
  A present organization ID cannot be empty, so the encoding is injective. Domain APIs
  continue to expose absence rather than the empty string.
- UTC timestamps use fixed canonical RFC 3339 form `YYYY-MM-DDTHH:MM:SS.sssZ` generated by
  the server. Ordering never relies on client-supplied timestamps.
- SHA-256 values are 32-byte BLOBs in SQLite. Public diagnostics may encode them as
  lowercase hexadecimal.
- Boolean values are integer `0` or `1` with explicit checks.

## 4. Migration 0001 logical DDL

The following is the schema contract. The implementation migration may add index names or
strict timestamp-format checks, but cannot merge the separated responsibilities or weaken
constraints without a reviewed design revision.

```sql
CREATE TABLE schema_metadata (
  singleton       INTEGER PRIMARY KEY CHECK (singleton = 1),
  schema_version  INTEGER NOT NULL CHECK (schema_version >= 1),
  migrated_at     TEXT NOT NULL,
  migration_id    TEXT NOT NULL,
  migration_sha256 BLOB NOT NULL CHECK (length(migration_sha256) = 32)
) STRICT;

CREATE TABLE terms_artifacts (
  terms_id         TEXT PRIMARY KEY,
  kind             TEXT NOT NULL CHECK (kind IN ('trial_terms', 'privacy_notice')),
  version          TEXT NOT NULL,
  locale           TEXT NOT NULL,
  state            TEXT NOT NULL CHECK (state IN ('draft', 'active', 'retired')),
  effective_at     TEXT NOT NULL,
  content_type     TEXT NOT NULL CHECK (content_type = 'text/markdown; charset=utf-8'),
  content_bytes    BLOB NOT NULL,
  content_sha256   BLOB NOT NULL CHECK (length(content_sha256) = 32),
  summary_bytes    BLOB NOT NULL,
  summary_sha256   BLOB NOT NULL CHECK (length(summary_sha256) = 32),
  created_at       TEXT NOT NULL,
  UNIQUE (kind, locale, version),
  UNIQUE (terms_id, content_sha256, summary_sha256)
) STRICT;

CREATE UNIQUE INDEX one_active_terms_per_kind_locale
  ON terms_artifacts(kind, locale)
  WHERE state = 'active';

CREATE TABLE accounts (
  account_id          TEXT PRIMARY KEY,
  subject_id          TEXT NOT NULL UNIQUE,
  state               TEXT NOT NULL CHECK (
    state IN ('active', 'reconsent_required', 'suspended', 'export_only', 'closed')
  ),
  accepted_terms_id   TEXT NOT NULL REFERENCES terms_artifacts(terms_id),
  mapping_revision    INTEGER NOT NULL CHECK (mapping_revision >= 1),
  created_at          TEXT NOT NULL,
  updated_at          TEXT NOT NULL
) STRICT;

CREATE TABLE external_identity_mappings (
  identity_mapping_id  TEXT PRIMARY KEY,
  issuer               TEXT NOT NULL,
  external_subject_id  TEXT NOT NULL,
  organization_key     TEXT NOT NULL,
  account_id           TEXT NOT NULL REFERENCES accounts(account_id),
  state                TEXT NOT NULL CHECK (state IN ('active', 'replaced', 'revoked')),
  mapping_revision     INTEGER NOT NULL CHECK (mapping_revision >= 1),
  created_at           TEXT NOT NULL,
  replaced_at          TEXT,
  UNIQUE (issuer, external_subject_id, organization_key, mapping_revision)
) STRICT;

CREATE UNIQUE INDEX one_active_mapping_per_external_identity
  ON external_identity_mappings(issuer, external_subject_id, organization_key)
  WHERE state = 'active';

CREATE UNIQUE INDEX one_active_external_identity_per_account
  ON external_identity_mappings(account_id)
  WHERE state = 'active';

CREATE TABLE agreement_receipts (
  receipt_id                 TEXT PRIMARY KEY,
  identity_mapping_id        TEXT NOT NULL REFERENCES external_identity_mappings(identity_mapping_id),
  account_id                 TEXT NOT NULL REFERENCES accounts(account_id),
  terms_id                   TEXT NOT NULL,
  terms_version              TEXT NOT NULL,
  content_sha256             BLOB NOT NULL CHECK (length(content_sha256) = 32),
  summary_sha256             BLOB NOT NULL CHECK (length(summary_sha256) = 32),
  action_version             TEXT NOT NULL CHECK (action_version = 'trial-agree-v1'),
  accepted_at                TEXT NOT NULL,
  provisioning_operation_id  TEXT NOT NULL,
  FOREIGN KEY (terms_id, content_sha256, summary_sha256)
    REFERENCES terms_artifacts(terms_id, content_sha256, summary_sha256),
  UNIQUE (identity_mapping_id, terms_id, action_version),
  UNIQUE (provisioning_operation_id)
) STRICT;

CREATE TABLE tenant_catalog (
  tenant_id        TEXT PRIMARY KEY,
  owner_account_id TEXT NOT NULL UNIQUE REFERENCES accounts(account_id),
  state            TEXT NOT NULL CHECK (state IN ('provisioning', 'active', 'export_only', 'closed')),
  created_at       TEXT NOT NULL,
  updated_at       TEXT NOT NULL
) STRICT;

CREATE TABLE workspace_catalog (
  workspace_id  TEXT PRIMARY KEY,
  tenant_id     TEXT NOT NULL REFERENCES tenant_catalog(tenant_id),
  kind          TEXT NOT NULL CHECK (kind IN ('initial', 'additional')),
  state         TEXT NOT NULL CHECK (state IN ('provisioning', 'active', 'export_only', 'closed')),
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL,
  UNIQUE (tenant_id, workspace_id)
) STRICT;

CREATE UNIQUE INDEX one_initial_workspace_per_tenant
  ON workspace_catalog(tenant_id)
  WHERE kind = 'initial';

CREATE TABLE scope_policies (
  scope_policy_id  TEXT PRIMARY KEY,
  version          INTEGER NOT NULL CHECK (version >= 1),
  state            TEXT NOT NULL CHECK (state IN ('draft', 'active', 'retired')),
  scopes_json      TEXT NOT NULL CHECK (json_valid(scopes_json)),
  created_at       TEXT NOT NULL,
  UNIQUE (scope_policy_id, version)
) STRICT;

CREATE TABLE account_scope_bindings (
  account_id       TEXT PRIMARY KEY REFERENCES accounts(account_id),
  scope_policy_id  TEXT NOT NULL REFERENCES scope_policies(scope_policy_id),
  bound_at         TEXT NOT NULL,
  binding_revision INTEGER NOT NULL CHECK (binding_revision >= 1)
) STRICT;

CREATE TABLE recovery_credentials (
  recovery_id       TEXT PRIMARY KEY,
  account_id        TEXT NOT NULL REFERENCES accounts(account_id),
  verifier_version  TEXT NOT NULL,
  verifier_bytes    BLOB NOT NULL,
  state             TEXT NOT NULL CHECK (state IN ('active', 'rotated', 'revoked')),
  issued_at         TEXT NOT NULL,
  rotated_at        TEXT,
  last_used_at      TEXT
) STRICT;

CREATE UNIQUE INDEX one_active_recovery_credential_per_account
  ON recovery_credentials(account_id)
  WHERE state = 'active';

CREATE TABLE provisioning_operations (
  provisioning_operation_id TEXT PRIMARY KEY,
  issuer                     TEXT NOT NULL,
  external_subject_id        TEXT NOT NULL,
  organization_key           TEXT NOT NULL,
  terms_id                   TEXT NOT NULL REFERENCES terms_artifacts(terms_id),
  action_version             TEXT NOT NULL,
  account_id                 TEXT NOT NULL UNIQUE REFERENCES accounts(account_id),
  tenant_id                  TEXT NOT NULL UNIQUE REFERENCES tenant_catalog(tenant_id),
  initial_workspace_id       TEXT NOT NULL UNIQUE REFERENCES workspace_catalog(workspace_id),
  receipt_id                 TEXT NOT NULL UNIQUE REFERENCES agreement_receipts(receipt_id),
  state                      TEXT NOT NULL CHECK (state IN ('committed')),
  committed_at               TEXT NOT NULL,
  UNIQUE (issuer, external_subject_id, organization_key)
) STRICT;

CREATE TABLE account_state_events (
  event_id       TEXT PRIMARY KEY,
  account_id     TEXT NOT NULL REFERENCES accounts(account_id),
  from_state     TEXT,
  to_state       TEXT NOT NULL,
  reason_code    TEXT NOT NULL,
  actor_kind     TEXT NOT NULL CHECK (actor_kind IN ('system', 'user', 'operator')),
  occurred_at    TEXT NOT NULL,
  mapping_revision INTEGER NOT NULL CHECK (mapping_revision >= 1)
) STRICT;

CREATE TABLE realization_outbox (
  outbox_id       TEXT PRIMARY KEY,
  operation_kind  TEXT NOT NULL CHECK (operation_kind = 'realize_initial_workspace'),
  tenant_id       TEXT NOT NULL REFERENCES tenant_catalog(tenant_id),
  workspace_id    TEXT NOT NULL REFERENCES workspace_catalog(workspace_id),
  state           TEXT NOT NULL CHECK (state IN ('pending', 'leased', 'done', 'failed')),
  attempt_count   INTEGER NOT NULL DEFAULT 0 CHECK (attempt_count >= 0),
  available_at    TEXT NOT NULL,
  lease_owner     TEXT,
  lease_expires_at TEXT,
  last_error_code TEXT,
  created_at      TEXT NOT NULL,
  completed_at    TEXT,
  UNIQUE (operation_kind, tenant_id, workspace_id)
) STRICT;

CREATE INDEX pending_realization_order
  ON realization_outbox(state, available_at, outbox_id);
```

`scope_policies.scopes_json` is additionally parsed through the same strict allowlist as
the current server scopes. `json_valid` alone is not authorization validation.

## 5. Repository ports

The code-level ports remain separate even though one adapter implements them with one DB:

```ts
interface ExternalIdentityRegistry {
  resolve(
    identity: ExternalIdentity,
    snapshot: ReadSnapshot,
  ): AccountIdentity | null;
}

interface AgreementLedger {
  currentTerms(locale: string, snapshot: ReadSnapshot): TermsArtifact;
  appendReceipt(
    input: VerifiedAgreement,
    tx: LifecycleTransaction,
  ): AgreementReceipt;
}

interface AccountRepository {
  get(accountId: string, snapshot: ReadSnapshot): TrialAccount | null;
  transition(input: AccountTransition, tx: LifecycleTransaction): TrialAccount;
}

interface TenantCatalog {
  resolveOwnedTenant(
    accountId: string,
    snapshot: ReadSnapshot,
  ): TenantBinding | null;
  createExclusive(
    input: NewTenantBinding,
    tx: LifecycleTransaction,
  ): TenantBinding;
}

interface WorkspaceCatalog {
  createInitial(
    input: NewWorkspaceBinding,
    tx: LifecycleTransaction,
  ): WorkspaceBinding;
}

interface ScopePolicyRepository {
  resolveForAccount(
    accountId: string,
    snapshot: ReadSnapshot,
  ): readonly LlmthinkServerScope[];
}

interface RealizationOutbox {
  enqueueInitialWorkspace(
    input: RealizationRequest,
    tx: LifecycleTransaction,
  ): void;
}
```

Only `ProvisionTrialAccount` receives a `LifecycleTransaction` capable of coordinating the
write ports. Individual repositories cannot commit independently. Read-side admission uses
one read transaction/snapshot for identity mapping, account state, tenant ownership,
workspace state, and scope policy.

### 5.1 Migration 0002: recovery and archive evidence

Migration 0002 adds three logically separate append-oriented records without moving thought
content into the lifecycle database:

- `recovery_requests` binds a verified recovery credential to one proposed exact external
  identity and remains pending until an operator approves or rejects it. The table contains no
  recovery plaintext. Only one pending request per account is allowed.
- `archive_receipts` records the archive format, SHA-256, byte length, item count, account,
  tenant, workspace, and server time. Archive bytes remain outside SQLite.
- `retention_transitions` records the start of the 30-day archive window and subsequent
  operational-data closure. It is evidence of lifecycle intent, not proof that backup expiry or
  physical deletion has completed.

Recovery approval atomically replaces the old mapping, increments `mapping_revision`, rotates
the active recovery verifier, and completes the request. Credential possession alone creates
only a pending request and neither returns thought data nor changes authorization.

## 6. First-provisioning transaction

Preparation outside the transaction:

1. verify JWT and construct exact external identity;
2. verify onboarding session, CSRF token, nonce, and displayed terms binding;
3. generate candidate random internal IDs and recovery secret;
4. derive the recovery verifier using the approved KDF;
5. load and hash no user-controlled unbounded data.

Transactional phase:

```text
BEGIN IMMEDIATE
  read active terms and compare exact terms ID/digests
  read active external identity mapping
  if present: read committed provisioning result and return ALREADY_PROVISIONED
  insert account
  insert active external identity mapping
  insert agreement receipt
  insert tenant catalog row in provisioning state
  insert initial workspace row in provisioning state
  insert fixed scope-policy binding
  insert recovery verifier
  insert committed provisioning operation
  insert account-state event
  insert pending realization outbox event
COMMIT
```

If a unique conflict occurs, rollback and perform one read transaction. Return the existing
committed account only when the exact external identity owns it. Never substitute a result
selected only by a colliding client-supplied operation ID.

The recovery plaintext is returned only by the transaction winner and only once. A retry
returns `recovery_credential_already_issued`, not the original secret. Losing the initial
display requires the audited recovery process; this avoids retaining recoverable plaintext.

## 7. Authorization snapshot

Admission resolves the following tuple in one read transaction:

```text
external identity
  -> one active mapping
  -> one account in permitted state
  -> one tenant owned by that account
  -> requested workspace belonging to that tenant
  -> one scope policy binding parsed through the server allowlist
  -> no required realization pending
```

Zero rows, multiple rows, inconsistent states, unknown scope entries, unsupported schema,
or database read failure returns `account_unavailable` and no `RequestContext`. The data
plane never attempts to repair the control plane.

## 8. Outbox realization and reconciliation

An outbox worker claims a bounded batch using a short transaction. A lease is identified by
an opaque process instance ID and expiration. Filesystem work occurs after commit.

For each event:

1. derive the target only through the existing repository's validated tenant/workspace key;
2. create or inspect the expected directory structure without following symlinks;
3. if absent, realize it atomically as supported by the repository;
4. if present, verify it matches the catalog identity and expected empty/initialized form;
5. mark tenant/workspace active and the outbox event done in one DB transaction;
6. on bounded retryable error, clear/expire the lease and schedule backoff;
7. on identity/path conflict, mark failed, keep access closed, and require operator review.

Reconciliation compares catalog/outbox state to repository observations. It reports orphan
directories, missing realizations, duplicate ownership, and impossible state combinations;
it does not assign ownership, delete data, or auto-promote an orphan.

## 9. Migration and cutover

### 9.1 Schema migration

- Migration files are immutable and embedded with expected SHA-256 digests.
- Startup reads `schema_metadata`; an empty DB may apply 0001 under an exclusive migration
  lock. Unknown newer, missing, partially applied, or digest-mismatched schema fails closed.
- Before a non-empty migration, create and verify an online backup and record only its safe
  path metadata, schema version, size, and digest—not lifecycle rows.
- A migration transaction updates schema and metadata together. Destructive column/table
  removal requires a later ADR and restore rehearsal.

### 9.2 Static JSON registry cutover

- Import is an explicit one-shot operator command, never automatic startup behavior.
- Validate the complete JSON with the current strict loader before opening a write
  transaction.
- Every imported mapping receives a new internal account/catalog representation but no
  fabricated agreement receipt. It starts `reconsent_required` unless separately matched
  to valid agreement evidence.
- Duplicate external identities, internal subjects, tenant owners, or workspaces abort the
  whole import. No first-wins behavior is allowed.
- Freeze the JSON digest, import once, read back exact counts and mappings without personal
  claims, then switch one configured authority from JSON to SQLite on restart.
- Never dual-write. Rollback before public enrollment may switch back to the unchanged JSON
  authority only if no SQLite-only account has been admitted.

## 10. Backup and restore

- Use the SQLite online backup API from a read connection, or an equivalent SQLite-supported
  consistent snapshot. Do not copy only the main file while WAL may contain committed data.
- Encrypt and access-control backup media according to the lifecycle database classification.
- A backup receipt records schema version, safe artifact identifier, byte size, digest,
  creation time, and verifier—not row values.
- Restore always targets a new absent path. Run `integrity_check`, `foreign_key_check`, schema
  digest validation, invariant queries, and catalog/outbox reconciliation before replacement.
- Replacement is an operator-gated atomic activation followed by service restart and bounded
  read-only checks. Ambiguous activation stops; it is not blindly retried.
- Thought data backup remains separate. A lifecycle restore and a thought-data restore must
  share an explicitly frozen recovery point or be reconciled with fail-closed missing data;
  neither side invents ownership from the other.

## 11. Required tests

- two concurrent first agreements for one identity produce exactly one account and tenant;
- different identities cannot collide into one account, tenant, workspace, or recovery row;
- absent and present `org_id` remain distinct and exact;
- terms activation racing with agreement cannot record undisplayed bytes;
- crash after DB commit and before directory creation resumes from one outbox event;
- crash after directory creation and before outbox completion completes without duplication;
- stale outbox lease is recoverable, while a live lease is not stolen;
- authorization never mixes mapping/account/catalog/scope rows from inconsistent snapshots;
- unknown scope, schema, state, migration, or catalog mismatch fails closed;
- static-registry import is all-or-nothing and never fabricates agreement;
- backup with active WAL restores all committed rows and no partial transaction;
- restore detects foreign-key violations, multi-owner conditions, missing realization, and
  orphan data without automatic repair;
- repository and log tests prove absence of email, token, recovery plaintext, thought content,
  and filesystem paths from unintended boundaries.
